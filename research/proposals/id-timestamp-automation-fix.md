# ID Timestamp Automation -- Eliminate Manual Entry of Permanent Identifiers

## Problem

Every brain artifact (IOR, insight, evaluation, proposal, report)
requires a permanent ISO 8601 UTC timestamp ID generated by running
`date -u +'%Y%m%dT%H%M%SZ'`. The ID is never reused, never changed
after publishing. The templates all state: "MUST generate with: date -u.
Estimating or rounding = GATE FAILURE."

Despite this, approximately 30% of IDs are manually typed rather than
generated from the command. The failure mode is consistent: the agent
types a timestamp from memory, rounds to a clean number (e.g.,
`20260719T230000Z`), or estimates slightly. The resulting ID is close
to correct but not exact -- permanently wrong, permanently visible,
and impossible to fix after publishing.

The latest instance: `20260719T230000Z` in the insight `agent-evolution.md`.
The actual time was `20260719T230209Z`. Off by 2 minutes and 9 seconds.
The agent knew the rule and violated it because rounding felt harmless.

This is a structural failure, not an attention failure. The current
gate ("not estimated, not rounded" in a checklist) is a volition-based
gate. Wording changes will not fix it (R6: volition = hope). The agent
must not be ABLE to type a timestamp by hand and pass verification.

## Proposed Solution

Three-layer fix: procedural gate at write time, verification at
Format Verification time, and CI validation at commit time. Each
layer catches what the previous layer misses.

### Layer 1: Procedural gate (write-X skills)

Add an explicit step to every write-X skill's Procedure section,
immediately before "Write the file":

```
### N. Generate the ID

Run `date -u +'%Y%m%dT%H%M%SZ'` and capture the output. Paste the
exact output into the `id:` field in the frontmatter. Never type the
ID digits by hand. The exec output is the authoritative value.
```

The Format Verification frontmatter item for `id:` changes from:
```
id: generated by running `date -u +'%Y%m%dT%H%M%SZ'` (not estimated, not rounded)
```
to:
```
id: exact output from `date -u +'%Y%m%dT%H%M%SZ'` exec call, pasted directly, never manually typed
```

### Layer 2: Format Verification check (write-X skills)

Add a verification item to every write-X skill's Format Verification
section:

```
- [ ] N. id verified: does not end in 000000Z, 000000Z, or other
      human-rounded patterns. If the seconds digits are all zeros,
      the ID is almost certainly manually typed. Re-run date -u
      and replace. (PASS / HALT)
```

This catches the most common failure mode -- the agent typing a clean
round number (`20260719T230000Z`) instead of the actual time.

### Layer 3: CI validation script (ascii-guard extension)

Add an optional validation pattern to the existing `ascii-guard.yml`
or a companion script. Before commit, scan changed markdown files in
the brain for frontmatter `id:` fields and flag any that:

1. Are not valid ISO 8601 format.
2. End in `000000Z` or `000000Z` (human-rounded patterns).
3. Are identical to another file's ID (duplicate check).
4. Are in the future (timestamp > current UTC time + 5 minutes, allowing
   for clock skew).

Failed validation produces a clear message: "ID `20260719T230000Z` in
file `research/insights/agent-evolution.md` appears to be manually
rounded. Run `date -u +'%Y%m%dT%H%M%SZ'` and replace."

### Implementation order

1. Update all 5 write-X skills (evaluation, insight, proposal,
   reflection, report) with Layer 1 and Layer 2 changes.
2. Add Layer 3 as a CI gate (can be done separately, lower priority
   since Layers 1-2 prevent the error at write time).

## Impact

**Positive:** Eliminates the ~30% manual ID failure rate. Every ID
becomes exact because the agent cannot pass verification with a
manually-typed timestamp. The exec call is the authoritative source.

**Risk:** Low. The changes are additive -- existing verification items
remain, new items add pre-existing checks. No existing behavior is
removed. The CI script (Layer 3) only scans IDs, does not block commits
initially (can be set to warn, then later upgraded to block).

**Cost:** Under 30 minutes. Five skills get two small additions each
(a new procedure step, a new verification item). The CI script is
optional and can follow later.

## Open Questions

1. Should Layer 3 block commits or warn only? Warning is safer for
   initial deployment -- prevents false positives from blocking
   legitimate work.
2. Should we also validate that the ID in the filename (for reflections)
   matches the ID in the frontmatter? This is a separate consistency
   check but related to the same failure class.
3. Should the write-X skills' procedure step for ID generation also
   include: "Store the ID in a variable or paste buffer BEFORE writing
   the rest of the file, so you are not tempted to type it later"?
