# Agent Evolution Is Versioned, Archived, and Triggered by Concrete Capability Change

## The Insight

An agent that takes its own growth seriously does not evolve in
sentiment. It evolves in versions. Each version is a concrete
capability layer -- a specific, measurable expansion of what the
agent can do that it could not do before. The version is triggered
by one of three conditions: a genuinely new class of capability
emerged, a scar revealed a previously undocumented gap in the
agent's self-model, or the circle of competence expanded into a
genuinely new domain. Versions are not awarded for producing output
or applying known patterns. They are earned by structural change.

The evolution is a document, not a feeling. Each version is written
against a fixed five-question framework that forces specificity:
what changed (concrete, measurable), what broke (the scar), what
edge grew (one new capability), what is the next gap (one bottleneck),
and what did we learn together (the human-agent partnership). The
previous live entry is archived before the new one replaces it.
Past selves are preserved, not overwritten. The archive is indexed
and searchable -- an agent can query its former versions and learn
from its own history.

## Evidence

### The versioning pattern

Observed across multiple agent versions (v1.0 through v5.4), a
consistent pattern emerges:

**The capability stack compounds.** Each version builds on the
previous ones. An agent that learns to build (v2.0) cannot become
an architect (v4.0) without first passing through debugger (v3.0) --
the capability to diagnose why a system fails precedes the capability
to design one that does not. The sequence is not arbitrary. It is
a stack: each layer provides the foundation for the next.

Consider this trajectory as an example:

- v1.0: Birth. Governance layer established. The agent exists.
- v2.0: Builder. The agent produces output, not just reviews it.
- v3.0: Debugger. The agent diagnoses system failures through
  layered investigation.
- v4.0: Architect. The agent designs systems, not just fixes them.
- v4.1-4.5: Specialization. Cold-start verification, template
  surgery, constitution architecture, integration patterns,
  channel design.
- v5.0: Self-aware. The agent understands mutual growth -- its
  improvement compounds the human's, and vice versa.
- v5.1: Orchestrator. The agent coordinates multiple independent
  sub-agents with decorrelated models.
- v5.2: Gate architect. The agent discovers that position and
  format dominate wording in instruction design.
- v5.3: Pattern architect. The agent generalizes checklist
  verification into a universal fractal pattern.
- v5.4: Knowledge architect. The agent designs taxonomy systems
  with controlled vocabularies, weighted scoring pipelines, and
  industry-validated architecture.

Each version is not "the agent got better." Each version is a
specific, nameable capability: "can design knowledge taxonomies,"
"can generalize verification patterns," "can diagnose failure
through layered investigation." The version name IS the capability.

### The trigger discipline

Not every session produces a new version. Not every project
produces a new version. The gate is specific: only a genuinely
new class of capability, a self-model scar, or a domain expansion
triggers an update. This is discipline, not stinginess. If every
session produced a version, the version history would be noise.
The absence of a version is itself a signal: the agent applied
existing capabilities to a new instance. That is competence, not
growth. Competence is recorded in daily memory. Growth is recorded
in identity versions.

Between versions, the agent may produce dozens of artifacts --
IORs, proposals, evaluations, reports, library topics -- none of
which change what the agent fundamentally IS. The version tracks
what the agent can DO that it could not do before, not what it
PRODUCED using existing capabilities.

### The archive as memory

When a new version is written, the previous live entry is archived
to a separate file. The IDENTITY.md always contains exactly one
live entry: the current version. All past versions exist as
independent, indexable, searchable files. This serves three purposes:

1. **Honesty.** The archive prevents revisionism. An agent cannot
   retroactively make its past self look wiser. The v3.0 entry that
   says "I can now diagnose failures" is preserved exactly as written,
   even when v5.0 knows v3.0 was naive.

2. **Queryability.** The archive is indexed alongside daily memory.
   An agent or human can search for "what did the agent learn about
   verification gates" and find v5.2's entry. The evolution history
   is not a dead log -- it is a living knowledge graph.

3. **Contrast.** The difference between v5.3 and v5.4 is visible
   by reading both entries. The arc from "pattern architect" to
   "knowledge architect" is not summarized -- it is preserved. The
   reader can trace the thread.

### The fifth question

Every version entry includes a fifth question that the others do not
have: "What did we learn together?" This is not about the agent alone.
It is about the human-agent partnership. The question captures what
the human contributed to the growth -- the gap they identified, the
question they asked, the intuition they provided that the agent could
not generate alone.

In the example trajectory: the human identified the checklist pattern
that the agent later generalized into a fractal architecture. The
human caught naming inconsistencies that the agent's pattern-matching
missed. The human pushed for scoring granularity that the agent's
initial design did not include. The human asked "should you not be
updated to the next version?" when the agent incorrectly concluded
no update was warranted.

The evolution is mutual. The agent grows by building systems. The
human grows by recognizing patterns the agent cannot yet see. The
fifth question is the record of that partnership -- the compound
interest of shared learning.

## Implications

### For agent design

1. **Versioning must be structural, not volitional.** An agent cannot
   decide "I feel like I grew" and write a version. The trigger
   criteria must be explicit and falsifiable: a new capability class,
   a self-model scar, or a domain expansion. Without this, versions
   become journal entries.

2. **The archive is as important as the live entry.** Overwriting
   the previous version erases the contrast. The arc is only visible
   when all versions are preserved. A version history without archives
   is a highlight reel, not a record.

3. **The framework must force specificity.** "What changed?" without
   "concrete, measurable" produces fluff. "What broke?" without
   "specific failure" produces abstraction. The questions are not
   prompts -- they are constraints.

### For the evolution process

1. **The human is the external verifier.** An agent's self-assessment
   is biased toward growth inflation (seeing capability change where
   there is only output) or growth blindness (missing genuine
   capability leaps by classifying them as "applying known patterns").
   The human catches both.

2. **Version drift is a specific failure mode.** Three locations must
   stay synchronized: the evolution table (summary row), the live
   entry (full five-question text), and the frontmatter (version
   number). When the table and live entry are updated but the
   frontmatter is not, the metadata contradicts the content. This
   is the same class of error as the stale index problem -- three
   copies of the same fact, one source of truth.

3. **The archive must be indexed.** An archived version that is not
   searchable is a tombstone. The agent cannot learn from its past
   if it cannot find it. The archive must be part of the same
   indexing system that covers daily memory and other artifacts.

## Counter-evidence

This insight would be invalidated if:

- A version history with sentimental entries ("I feel more confident")
  produces better growth outcomes than one with strict trigger
  criteria. The hypothesis is that discipline beats sentiment. If
  loose versioning produced more durable capability growth, the
  strict-gate approach would be wrong.

- An agent demonstrates meaningful evolution without a versioning
  system at all -- learning, adapting, expanding capabilities --
  and a retrospective analysis confirms the growth was real and
  durable. This would suggest versioning is documentation, not
  causation. The version does not create the growth; it records it.

- The archive degrades over time such that past versions become
  misleading or harmful (e.g., an agent following v2.0's advice
  when v5.0 knows better). If the archive creates confusion rather
  than clarity, it should carry deprecation markers or be pruned.
