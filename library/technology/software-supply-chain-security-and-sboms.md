# Software Supply-Chain Security Requires Inventory, Verifiable Provenance, and Operational Remediation

Software supply-chain security fails when an organization treats a component list as proof that released software is trustworthy. An actionable system joins a current software bill of materials (SBOM) to verified build provenance, protected release processes, vulnerability context, and an operating loop that can identify, prioritize, and remediate affected deployments [1][2][4].

## Background

Software rarely moves directly from one author's source code to one user's machine. A release may incorporate first-party modules, open source packages, commercial libraries, generated files, build tools, container images, package repositories, continuous-integration services, signing systems, and distribution infrastructure. Each dependency and transformation creates a place where an error, compromised credential, malicious contributor, vulnerable component, or altered artifact can affect downstream users. NIST therefore treats secure development as a lifecycle discipline and recommends that producers collect, protect, maintain, and share provenance for every component of each release, including through an SBOM [2].

The phrase "software supply chain" describes both a graph of component dependencies and a sequence of production steps. These views answer different questions. The dependency graph asks what is inside the delivered software and which component depends on which other component. The production sequence asks who or what transformed source and inputs into an artifact, under which process, and with which controls. CISA's 2026 minimum-elements guidance defines an SBOM as a nested inventory and requires component relationships that can support a dependency graph; SLSA provenance separately records the builder, build process, external parameters, and resolved inputs for an artifact [1][4]. An inventory without process evidence cannot establish how the listed components became the delivered binary, while provenance without a sufficiently complete component inventory can leave vulnerable transitive dependencies invisible.

Widely distributed compromises made the difference concrete. In the SolarWinds case, CISA analyzed a trojanized, legitimately signed Orion component delivered through a normal update path. The malicious dynamic-link library was installed by the legitimate SolarWinds installer and gave the operator remote capabilities on affected systems [10]. A valid release signature therefore did not establish that the build process or signed payload was benign. In March 2024, CISA also warned that malicious code had been embedded in XZ Utils versions 5.6.0 and 5.6.1 and advised users to move to an uncompromised version [13]. That response depended on identifying an exact component and version across systems, which is one of the operational uses that a current, machine-readable SBOM can support.

Government and standards work translated these incidents and broader dependency risk into common technical practices. NIST's Secure Software Development Framework, version 1.1, recommends protecting development environments, verifying tool integrity and provenance, archiving release evidence, collecting component provenance, checking acquired components, and building in controlled environments [2]. NIST's cybersecurity supply-chain guidance places these controls inside organization-wide risk management rather than treating supply-chain security as a single scanner or developer task [12]. CISA's 2026 SBOM guidance updates the 2021 NTIA baseline with additional metadata for author signatures, formats, generation context, tools, versions, component hashes, and licenses, while requiring coverage of transitive dependencies and machine-processable delivery [1].

Two open standards dominate current SBOM exchange. SPDX is an international open standard published as ISO/IEC 5962:2021 for communicating component and metadata information associated with software packages [6]. CycloneDX is standardized as ECMA-424 and represents components, services, dependencies, vulnerabilities, cryptographic artifacts, machine-learning models, attestations, and related supply-chain data in a structured machine-readable format [7]. CISA identifies SPDX and CycloneDX as the two formats widely used by software ecosystem stakeholders and advises organizations to accept widely used, interoperable, machine-processable formats rather than requiring one proprietary representation [1]. The important control is not the brand of format but whether producers and consumers can exchange, validate, update, and act on the required data.

SBOM practice developed because vulnerability response requires a reliable mapping from a new advisory to deployed software. CISA's current minimum-elements model includes component producer, name, version, identifiers, dependency relationship, license, executable hash and hash algorithm, plus metadata about the SBOM itself [1]. These fields can support correlation with vulnerability databases and security advisories, but the SBOM does not determine whether vulnerable code is reachable or exploitable in a particular product. CISA-hosted community VEX guidance defines a companion statement that communicates a product or component's status with respect to a vulnerability, including whether it is affected; that document also states that it is not official CISA policy [11]. Inventory and vulnerability status are therefore related records, not interchangeable ones.

The earliest cross-sector proof work also exposed limitations that remain central. In NTIA's 2019 healthcare proof of concept, medical-device manufacturers generated SPDX or SWID records and healthcare organizations used them to identify vulnerable and end-of-life components. The exercise also found missing patch status, difficult dependency extraction, incomplete automation, identifier problems, and configuration risks that the SBOM could not reasonably represent [9]. An empirical study published at ICSE 2023 likewise found practitioner concerns about incomplete minimum fields, data and tooling integrity, limited consumption, and uncertain handling of vulnerabilities with limited exploitability [8]. These findings reject the idea that producing a file is the same as operating a control.

This topic stays within software engineering and technology: component inventory, machine-readable formats, build provenance, artifact integrity, release controls, and integration with development and operations. General cybersecurity strategy is covered by the broader cybersecurity topic, while open source licensing and maintainer governance are covered by the digital-commons topic. The author's synthesis is that supply-chain security becomes actionable only when four evidence layers remain connected: what components are present, how the artifact was produced, whether the evidence can be authenticated and checked, and who must act when risk changes [1][2][4][5].

## Core Concepts

### The supply chain is both a dependency graph and a transformation graph

A dependency graph represents components and the relationships required for one component to operate another. CISA's 2026 baseline expects coverage of all components, including transitive dependencies, with no minimum depth; distinct instances with different metadata should be listed separately [1]. This requirement matters because a top-level application can inherit risk through a library selected by another library, a base image beneath a container, or a tool that inserts output into a build. A flat list may reveal names but lose the paths needed to identify which product, service, or release depends on a component.

A transformation graph represents the steps that convert source and inputs into an artifact. Those steps can include fetching dependencies, generating code, compiling, testing, packaging, signing, publishing, and mirroring. SLSA provenance identifies a build type, external parameters, builder, outputs, and resolved dependencies within an in-toto attestation model [4]. The in-toto framework extends this idea across a pipeline: a project owner declares authorized steps and functionaries, each step produces signed link metadata, and a consumer verifies that the delivered product followed the declared layout [5]. The transformation graph can therefore expose an unauthorized step or unexpected builder even when the component names appear normal.

The two graphs overlap but should not be collapsed. An SBOM's dependency entry can say that application A includes library B. Provenance can say that builder C used source revision D and declared input E to produce artifact F. Neither statement alone proves that the released artifact contains exactly the components claimed by the SBOM. The author's assessment is that a mature release should bind the SBOM and provenance to the same immutable artifact digest, then verify both before publication or deployment. This is a synthesis of CISA's component-hash requirement, NIST's integrity guidance, and SLSA's artifact-subject model [1][2][4].

### An SBOM is evidence about composition, not a vulnerability verdict

The minimum useful SBOM identifies both the document and the software it describes. CISA's 2026 metadata fields include the SBOM author and signature, data-format name and version, generation context, timestamp, tool name and version, and SBOM version [1]. Component fields include producer, name, version, at least one useful identifier, dependency relationships, license, executable hash value, and the hash algorithm [1]. The separation prevents ambiguity between the entity that made the software, the entity that generated the record, and the tool used to generate it.

Component identity is harder than a human-readable name. Different ecosystems can reuse names, distributors can repackage upstream code, and one component can have aliases. CISA recommends common machine-processable identifiers such as Common Platform Enumeration and Package-URL, while permitting commit hashes, UUIDs, and intrinsic identifiers when useful [1]. The 2019 healthcare proof of concept found that inconsistent naming interfered with vulnerability correlation, demonstrating why an identifier must work as a database key rather than merely look understandable to a person [9]. Unknown values should be explicit, because an empty field cannot distinguish unavailable information from accidental omission or deliberate redaction [1].

Generation context explains what an SBOM could observe. Source analysis before a build can identify declared packages but miss generated or vendored code. Build-integrated generation can see resolved versions and some transitive inputs. Binary analysis after a build can observe artifacts actually present but may lose package-manager metadata or source relationships. CISA now requires the lifecycle phase and available data to be identified and advises a new SBOM for each release or component update [1]. The author's synthesis is that organizations should retain more than one view when the risk warrants it and reconcile differences rather than treating any generator as an oracle [1][8][9].

Completeness is a property to test, not infer from a digital signature. A signature can provide assurance that an identified author signed the SBOM and that the signed bytes were not changed afterward [1]. It cannot prove that the author discovered every dependency, resolved every alias correctly, or selected an adequate tool. CISA explicitly separates source and integrity validation from accuracy, coverage, and completeness; it suggests independent repositories or binary analysis as possible comparison sources [1]. The ICSE practitioner study makes the same distinction between data integrity and tooling integrity, including both tool competence and tool compromise [8].

### Machine-readable standards make exchange possible but do not make data correct

SPDX and CycloneDX provide common schemas that tools can generate and consume. ISO/IEC 5962:2021 defines SPDX as a format for package, file, snippet, and associated metadata information [6]. ECMA-424 defines CycloneDX as a structured format for components, services, dependencies, vulnerabilities, licenses, attestations, and other transparency data [7]. Both can represent more information than the minimum baseline, and each evolves through versioned specifications. CISA therefore requires the format name and version and warns against deprecated versions that current consumers may not support [1].

Interoperability has three layers. Syntactic interoperability means a parser can read the document. Semantic interoperability means producer and consumer interpret fields and relationships the same way. Operational interoperability means the record arrives at the right time, remains associated with the correct release, and can enter inventory, vulnerability, policy, and incident workflows. The first is largely a schema problem; the second depends on identifiers and conventions; the third depends on lifecycle design. This three-layer model is the author's synthesis of the standard specifications, CISA's delivery requirements, and the healthcare proof-of-concept findings [1][6][7][9].

Organizations should avoid converting between formats without testing what is lost. A successful conversion may preserve package names while dropping relationships, hashes, attestations, or extension fields. The receiving system should validate the declared schema, required fields, identifiers, relationship consistency, and artifact binding after transformation. No inspected source establishes that every SPDX and CycloneDX feature has a lossless counterpart; compatibility should therefore be demonstrated for the organization's selected profiles rather than assumed from both documents being called SBOMs [1][6][7].

### Vulnerability correlation requires context, triage, and a remediation owner

An SBOM creates a candidate match between a component and external security information. A useful pipeline normalizes identifiers, maps the exact component version to advisories, determines where the component is deployed, adds evidence about exploitability and exposure, assigns priority, and tracks remediation. NIST says SBOM repositories should integrate with vulnerability detection so organizations can receive automated alerts for applicable risks [3]. CISA says VEX or CSAF can narrow the set of potentially affected components by carrying vulnerability status from a trusted producer [1].

A match is not yet a finding that a product is exploitable. A vulnerable package may contain code that a product does not invoke, may be built without the affected feature, or may be protected by a compensating control. Conversely, absence from a database does not prove safety, because vulnerabilities may be unknown or identifiers may fail to match. The CISA-hosted community VEX minimum requirements provide a format-independent way to state product or component status with respect to a vulnerability, but VEX itself depends on the authority, freshness, and reasoning of its issuer [11]. The ICSE study found that exploitability assessment was often manual and domain-dependent and that practitioners lacked clear handling for limited or uncertain exploitability [8].

Prioritization should combine at least five questions: Is the exact component and version present? Is the affected code or configuration reachable? Is exploitation known or plausible in the deployment context? What is the business or safety impact? Is a fixed version or mitigation available? This is the author's operational synthesis, not a prescribed score from one source. It follows from NIST's risk-based C-SCRM model, the SBOM/VEX distinction, and the healthcare exercise's use of external risk scores and compensating controls [9][11][12]. A team should record the evidence and owner for each answer so that a change in advisory status or deployment context can reopen the decision.

Remediation closes the loop. A system that produces accurate alerts but cannot upgrade, isolate, rebuild, or retire affected software has transparency without risk reduction. NIST's SSDF recommends processes to update deployed components while managing transitions and to record and triage discovered issues in the development workflow [2]. CISA requires a new or corrected SBOM when a build, release, component, dependency, or underlying record changes [1]. The output of remediation should therefore include both a changed artifact and refreshed evidence, not a ticket closed solely because a scanner stopped reporting the old identifier.

### Provenance answers how an artifact was built and which builder must be trusted

SLSA defines provenance as verifiable information about where, when, and how an artifact was produced. Its build track progresses from no guarantees at L0, to available provenance at L1, signed provenance from a hosted build platform at L2, and a hardened build platform at L3 [4]. The levels describe increasing resistance to mistakes and tampering; they do not claim that an artifact has no vulnerabilities. L1 provenance may be incomplete or unsigned and is explicitly easy to forge, while higher levels place stronger requirements on the builder and evidence [4].

The builder identity defines a trust boundary. SLSA's model treats the builder as the transitive closure of the hardware, software, control plane, and people that must faithfully execute the build and record provenance [4]. A signature is useful only if the verifier accepts the signer for that specific builder and checks the artifact digest, parameters, source revision, and policy. Accepting any valid signature would establish an identity without establishing authorization. The verifier must know what an expected build looks like and reject provenance that is validly signed but inconsistent with that expectation [4].

In-toto provides a broader layout-and-link model. Authorized parties sign metadata for defined steps, and a consumer verifies the chain against a project owner's policy [5]. Its design recognizes partial compromise: threshold signatures and separation of roles can preserve assurance even when one key or step is compromised. The 2019 evaluation compared deployments against historical supply-chain attacks and found that the examined cloud-native and reproducible-build integrations would have prevented most of the analyzed cases, while also documenting attacks outside particular deployment assumptions [5]. The result supports policy-bound attestations, not the claim that cryptographic metadata eliminates every supply-chain attack.

Reproducible builds are complementary evidence. Independent parties can rebuild source and compare outputs, reducing reliance on one build service, but reproducibility does not by itself prove that the source is benign or that users received the independently checked artifact. The in-toto study describes independent rebuilders producing attestations and uses TUF for compromise-resilient distribution of verification roots and metadata [5]. The author's synthesis is that provenance establishes an accountable production claim, reproducibility can test that claim independently, and secure update frameworks protect delivery of artifacts and trust metadata. Each covers a different failure boundary [4][5].

### Secure development and release controls produce the evidence

Supply-chain evidence is trustworthy only if the environments that create it are protected. NIST's SSDF recommends restricting and monitoring development tools, verifying tool integrity and provenance, using controlled build environments, reviewing code, safeguarding release files and evidence, and retaining provenance for each release [2]. These practices reduce the chance that an attacker can modify source, inject behavior during a build, replace an artifact after a build, or falsify the record used by consumers.

Separation of duties raises the cost of a single compromised credential. Source changes can require peer review; build services can generate provenance without allowing a developer to edit it; signing keys can be isolated from general-purpose build workers; publication can require verification of artifact digests and attestations. No one source prescribes one universal architecture for every organization, but NIST, SLSA, and in-toto all distinguish the producer's intent from independently generated or independently verified evidence [2][4][5]. The appropriate strength should reflect the consequence of compromise, the sensitivity of the software, and the feasible attacker model.

The strongest practical control is a policy gate that consumes evidence rather than merely stores it. A release policy can require an approved source repository and revision, a recognized builder, a minimum provenance level, an SBOM that passes schema and coverage checks, accepted licenses, no disallowed components, and disposition of applicable high-priority vulnerabilities. A deployment policy can independently verify the artifact digest and attached evidence. This gate design is the author's synthesis of SSDF practices, SLSA verification, CISA minimum elements, and in-toto layouts [1][2][4][5]. It should fail visibly when evidence is absent, stale, malformed, unauthorized, or inconsistent rather than silently treating missing data as approval.

### Actionability is a maintained operating system, not a document

An operational supply-chain system has a feedback loop: generate evidence during each release, validate and bind it to the artifact, distribute it with controlled access where needed, ingest it into an inventory, correlate it with new intelligence, decide applicability, remediate, and regenerate evidence. CISA's practices cover update accommodation, comprehensive coverage, timely delivery, explicit unknowns, release frequency, and machine-processable data [1]. NIST connects component provenance to operations and incident response, not only acquisition [2][3].

Freshness requires event-driven updates. A new release, changed dependency, corrected identifier, revised vulnerability status, or discovered omission can invalidate an earlier decision. CISA says every software version or update should have an associated SBOM and that corrected information should trigger a revised SBOM [1]. VEX and other advisories also need their own timestamps and product identifiers because an "not affected" statement for one build cannot automatically be transferred to a later build [11]. The author's assessment is that freshness service levels should be defined for each artifact type and enforced by automation.

Useful metrics measure decisions and outcomes rather than file counts. Candidate measures include the percentage of release artifacts with verified provenance, the percentage with validated SBOMs bound to the artifact digest, identifier match rates, unresolved unknown fields, time from advisory publication to affected-product identification, time to VEX or applicability decision, time to mitigation, and the number of deployments still running a superseded vulnerable component. These measures are the author's proposed implementation framework derived from the operating requirements in the cited guidance [1][2][3][4]. A rising count of generated SBOMs can coexist with worsening security if records are incomplete, stale, or unused.

## Evidence

### SolarWinds shows why signatures and component lists are insufficient alone

CISA's malware analysis examined trojanized Orion artifacts delivered as part of SolarWinds updates. The modified `SolarWinds.Orion.Core.BusinessLayer.dll` was installed by a legitimate installer, contained an obfuscated backdoor, and carried a SolarWinds digital signature whose certificate CISA treated as compromised [10]. The method was technical reverse engineering of identified malicious files, including hashes, certificate information, behavior, and update packaging. The finding demonstrates a compromise inside a trusted production and distribution path rather than a user downloading an obviously unrelated binary.

The case supports two bounded conclusions. First, verifying that an artifact was signed by a vendor was not sufficient because the attacker affected what the trusted process signed. Second, component identity and affected-version information were essential to incident response, but an SBOM by itself would not have proved that the build process was uncompromised. Provenance generated by an independent or hardened builder and checked against an expected build policy addresses a different part of the problem [2][4][10]. The case does not prove that any specific current provenance framework would have prevented SolarWinds under every deployment; that result depends on where the compromise occurred and which parties remained trustworthy.

### XZ Utils shows the value of precise version inventory and the limits of static trust

CISA's March 2024 alert reported malicious code in XZ Utils versions 5.6.0 and 5.6.1 and recommended moving to an uncompromised version, hunting for malicious activity, and reporting positive findings [13]. The advisory was a rapid operational notice based on reports and ecosystem investigation rather than a controlled experiment. Its practical question was exact and time-sensitive: which systems contain the identified versions, and can operators replace them safely?

A complete SBOM inventory could accelerate that first query across products and deployments. Dependency relationships could identify applications and images that inherited the library transitively, while hashes could distinguish artifacts when package labels were ambiguous [1]. The alert also exposes the boundary of inventory: knowing that a package version is present does not reveal how malicious behavior entered the source or build, whether a particular runtime path activated it, or whether an attacker already used it. Provenance, review history, build isolation, runtime investigation, and remediation remain separate controls [2][4][13].

### The in-toto evaluation tests policy-bound attestations against historical attacks

Torres-Arias and coauthors introduced in-toto at USENIX Security 2019. Their framework has a project owner sign a layout defining authorized steps and functionaries; participants sign link metadata for work performed; and a client verifies the delivered product and chain against those requirements [5]. The paper evaluated the design against 30 historical software supply-chain compromises and described deployments in cloud-native, hybrid-cloud, and cloud-agnostic settings. For the integrations analyzed, the authors reported that cloud-native and reproducible-build deployments would have prevented 83 percent and 90 percent of the examined historical attacks, respectively [5].

The evidence is a retrospective control analysis plus implementation cases, not a randomized field trial. Results depend on the selected attacks, the correctness of each modeled deployment, protection of the project owner's root keys, and adherence to verification. The paper also notes attack-specific differences: a deployment that does not build binaries cannot prevent a build compromise through that same control, while threshold mechanisms matter for key-compromise cases [5]. The bounded finding is that signed, policy-constrained step metadata can detect or prevent many classes of unauthorized transformation that artifact signing or isolated step security does not cover.

### The healthcare proof of concept tests whether SBOMs can cross an organizational boundary

NTIA's 2019 healthcare proof of concept involved medical-device manufacturers producing SPDX or SWID SBOMs and healthcare delivery organizations consuming them for procurement, asset, risk, and vulnerability-management use cases [9]. Participants exchanged records through a cloud file share, agreed constrained profiles for the flexible formats, and combined SBOM data with external vulnerability assessments. Healthcare organizations used the records to identify vulnerable and end-of-life components and consider mitigations [9]. This was a practical cross-organizational exercise rather than a population-wide estimate.

The limitations are as informative as the benefits. Manufacturers had to draw from multiple sources to describe integrated software; dependency extraction was difficult; patch status and some product-identification details were missing; configuration vulnerabilities did not fit the SBOM; and dedicated risk-management tools did not directly ingest the records [9]. The proof of concept found that industry-agnostic formats could serve healthcare, but it did not establish full automation or complete component discovery. The evidence supports SBOMs as a useful transfer mechanism when paired with profiles and external analysis, not as a self-sufficient risk assessment.

### Practitioner research identifies integrity, adoption, and exploitability gaps

Xia and coauthors used a mixed qualitative and quantitative method for the ICSE 2023 study: 17 practitioner interviews across 13 organizations and seven countries informed 26 statements, followed by a survey with 65 valid respondents from 15 countries [8]. The study examined production and consumption, data fields, distribution, integrity, vulnerability use, tooling, and adoption. Sixty-three point one percent of survey respondents agreed that generated SBOMs did not always meet the then-current minimum data-field baseline, and interviewees distinguished protection against tampering from the competence and security of generation tools [8].

The study also found limited consensus and operational maturity. Participants raised the need for secure distribution, integrity validation, better tooling, and a way to communicate vulnerabilities whose exploitability was limited or uncertain [8]. Its sample was recruited from practitioners already connected to SBOM work and was modest in size, so the percentages should not be generalized to all software organizations. The value of the study is diagnostic: it documents that the hardest problems extend beyond choosing a format and include incentives, data quality, trust, and action after a match.

### Current standards converge on complementary evidence rather than one universal artifact

CISA's 2026 guidance, NIST's SSDF, SLSA 1.2, SPDX, and CycloneDX come from different institutions and have different normative scopes [1][2][4][6][7]. CISA defines baseline SBOM fields and lifecycle practices. NIST defines secure development tasks, including component provenance and controlled builds. SLSA defines graduated source and build assurance and a provenance predicate. SPDX and CycloneDX define exchange models. Their convergence is functional rather than identical: machine-readable inventory, authenticated provenance, protected production, and downstream verification are separate but composable capabilities [1][2][4][6][7].

This standards comparison is document analysis, not proof that implementations conform. A tool can emit valid SPDX while omitting transitive components; a builder can produce signed provenance at a low assurance level; and a consumer can store both artifacts without verifying either. CISA explicitly states that signatures do not establish accuracy, coverage, or completeness, and NIST frames SBOMs as complements to existing supply-chain risk management rather than replacements [1][3]. The evidence therefore supports a layered architecture with testable gates, while leaving each organization responsible for validating its tools, profiles, policies, and operating response.

## Implications

### For software producers

Generate the SBOM and provenance inside the release process, not as a retrospective compliance exercise. Build-time evidence has access to resolved dependency versions, source revisions, builder identity, and output digests that may be impossible to reconstruct later. CISA requires the generation context to be declared and warns that lifecycle phases expose different data, while NIST notes that retroactively generated SBOMs may not reproduce the dependencies used at build time [1][3]. A producer should bind the SBOM and provenance to the released artifact's digest and publish them as versioned release evidence.

Protect the evidence path from the same compromise it is intended to reveal. If a build worker can modify the artifact, SBOM, provenance, and signature under one unrestricted identity, the records may agree while all are false. NIST recommends controlled build environments, tool-provenance checks, separated retention of integrity information, and protected release files [2]. SLSA's higher build levels require a hosted and then hardened build platform, and in-toto permits threshold and role policies across steps [4][5]. The appropriate design may range from a managed hosted builder to isolated high-assurance infrastructure, but trust boundaries and signer authorization should be explicit.

Treat unknown and incomplete data as managed risk. CISA's baseline calls for explicit unknowns and distinguishes unavailable information from information purposefully withheld [1]. A release gate can allow a documented exception when a legacy binary has no producer identifier, but it should preserve the uncertainty, owner, reason, and expiry date. Silently replacing unknown values with guesses makes later matching less reliable. The author's assessment is that unknown-field counts and exception age belong on the same dashboard as vulnerability findings because both affect the confidence of decisions.

Design updates as atomic evidence changes. When a dependency changes, the producer should issue the new artifact, SBOM, provenance, vulnerability status, and release metadata as one coherent set. CISA expects an SBOM for each release and revision after corrected information [1]. NIST expects provenance to be updated whenever components change [2]. A consumer should be able to verify that every document refers to the same release rather than combining an old SBOM with a new binary or a VEX statement for a different component version.

### For platform and DevSecOps teams

Make secure defaults easier than manual exceptions. Central build services can generate signed provenance, isolate credentials, retain logs, attach SBOMs, and enforce publication policy across many teams. SLSA Build L2 and L3 use hosted and hardened build platforms precisely because a common service can reduce the number of independent environments that must be trusted [4]. NIST recommends monitoring toolchains and verifying tool integrity and provenance [2]. A platform should expose the actual builder identity and policy results rather than hiding them behind a generic green check.

Validate more than syntax. An ingestion gate should parse the declared format version, verify signatures, confirm the artifact hash, require baseline metadata and component fields, detect duplicate or contradictory identities, build the dependency graph, and compare source-, build-, and binary-derived views where available. CISA separates signature validation from accuracy, coverage, and completeness and suggests independent evidence for quality checks [1]. The author's proposed rule is fail closed for malformed or unbound evidence and route uncertain completeness to an explicit risk decision rather than presenting both as the same failure.

Preserve evidence for incident response. The relevant question after a compromise may be which releases used a particular builder, input digest, signing key, tool version, or dependency, not only which products list one package name. NIST recommends securely archiving release files, integrity information, and provenance [2]. SLSA provenance records build parameters and builder identity, while CISA's 2026 SBOM metadata records generator and format versions [1][4]. Retention should cover the supported life of the release and the investigation horizon defined by the organization's risk model.

### For vulnerability-management and operations teams

Build an asset-to-component map before the emergency. An SBOM repository that is not connected to deployed assets cannot answer where an affected package is running. NIST recommends cataloging purchased, open source, and in-house software and integrating vulnerability detection with SBOM repositories [3]. CISA requires dependency relationships and comprehensive transitive coverage [1]. Operations should connect each deployed artifact digest to product, environment, owner, criticality, and current evidence set.

Separate candidate matches from applicability decisions. A scanner match should open an assessment, not automatically prove exploitability or automatically dismiss the issue. VEX can carry a producer's affected status, but the consumer still needs to authenticate the source, verify product and version identity, and consider its deployment context [1][11]. The 2023 practitioner study found uncertainty around limited exploitability and dependence on expert judgment [8]. Record the reason for "not affected," the evidence inspected, the issuing authority, and the conditions that would invalidate the decision.

Measure response latency at distinct stages. Time to identify affected assets measures inventory quality. Time to decide applicability measures identifier, VEX, and engineering effectiveness. Time to mitigate measures upgrade and operational capacity. Time to verify closure measures whether the deployed artifact and evidence actually changed. These are the author's proposed metrics based on the lifecycle responsibilities in CISA and NIST guidance [1][2][3]. Combining them into one mean time to remediation can hide whether the bottleneck is discovery, analysis, release, or deployment.

### For procurement and supplier management

Request capabilities that can be tested, not a one-time document. A contract or acquisition profile can specify accepted current formats, minimum fields, transitive coverage, delivery mechanism, update frequency, signatures, artifact hashes, support for vulnerability-status statements, correction procedures, and retention. CISA says these practices should be made explicit in policies, contracts, or arrangements and that authorized users should be able to integrate SBOM data into trusted tools [1]. NIST positions the SSDF as a common vocabulary that acquirers can use with suppliers [2].

An SBOM requirement should not displace broader due diligence. NIST's C-SCRM guidance addresses malicious functionality, counterfeit products, vulnerable development practices, supplier visibility, and risk assessment across organizational levels [12]. The NIST SBOM page explicitly says acquirers that cannot ingest, analyze, and act on the data are unlikely to improve their posture and that SBOMs complement rather than replace vendor risk assessment and vulnerability management [3]. Procurement should therefore test sample records and update flows before accepting a supplier's statement that SBOMs are available.

Avoid demanding unnecessary public disclosure. CISA allows access controls for unauthorized parties so long as authorized sharing and trusted-tool integration remain possible [1]. The ICSE study found practitioner concern about sensitive data and support for authenticated access in proprietary settings [8]. The author's assessment is that disclosure should be proportional: component transparency needed for risk management should be available to authorized consumers, while distribution policy can protect genuinely sensitive architecture details. Secrecy should not become a blanket justification for untestable claims.

### For open source maintainers and downstream users

Do not shift all responsibility to upstream volunteers. A maintainer can publish release manifests, signed artifacts, provenance, and security advisories, but downstream integrators choose combinations, patches, build flags, containers, and deployment contexts. CISA's model distinguishes component producer from SBOM author because the entity generating a product-level SBOM may differ from the upstream creator [1]. The durable-commons topic further shows that open licensing, governance, release engineering, and maintenance capacity are separate institutional layers. Downstream organizations should contribute fixes and tooling while maintaining their own integration evidence.

Package ecosystems can create leverage through common conventions. Standard identifiers, lock files, registry metadata, build attestations, and signed release records can let many producers generate higher-quality evidence without designing a private system. SPDX, CycloneDX, SLSA, and in-toto provide interoperable foundations [4][5][6][7]. The author's assessment is that ecosystems should publish constrained profiles and conformance tests, because flexible standards become operational only when participants agree which fields, relationships, signing rules, and delivery locations are required.

### A staged implementation model

Stage one is visibility. Inventory release artifacts, assign owners, generate an SBOM at build time, validate schema and minimum fields, and connect artifact digests to deployments. Stage two is response. Correlate components with advisories, support VEX or equivalent applicability records, define triage rules, and measure identification and remediation latency. Stage three is integrity. Generate and verify provenance, isolate build and signing roles, enforce source and builder policy, and retain evidence. Stage four is continuous assurance. Compare independent component views, test completeness, use hardened builders for critical products, exercise incident queries, and improve controls from observed failures. This staged model is the author's synthesis of CISA, NIST, SLSA, and in-toto guidance [1][2][4][5].

Stages should not be mistaken for universal maturity labels. A safety-critical device may need hardened build controls before broad automated vulnerability correlation, while a large enterprise may gain immediate value from deployment inventory before every supplier supports provenance. The sequence should be risk-based, but each stage should produce a verifiable capability rather than a policy statement. A practical acceptance test asks whether the organization can take a newly disclosed component version, identify affected deployed artifacts, explain how each was built, authenticate its evidence, assign an owner, remediate, and prove that the replacement reached production [1][2][3][4].

### Limits and decision rule

SBOMs do not reveal unknown vulnerabilities, malicious logic that has no known component identifier, unsafe configuration, compromised runtime credentials, or every copied fragment. Provenance does not prove source code correctness, and a hardened builder cannot compensate for an authorized malicious source change that passes policy. Signatures do not prove completeness, and VEX statements can be wrong or stale. These limits follow from the distinct scopes of the inspected standards and from the healthcare and practitioner studies [1][4][8][9][11].

The single worst failure is false assurance: publishing formally valid evidence that no downstream control verifies or can act upon. The preventive rule is to connect every artifact to an owner, every claim to an authenticated source, every release to current inventory and provenance, every vulnerability match to an applicability decision, and every decision to a tested remediation path. This is the author's synthesis. It converts software supply-chain security from document production into a closed, auditable control loop while preserving uncertainty where the evidence is incomplete [1][2][3][4][5].
