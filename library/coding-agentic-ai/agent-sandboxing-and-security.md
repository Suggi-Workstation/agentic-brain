# Agent Sandboxing and Security -- Why Tool-Using Agents Need Hard Boundaries Outside the Model

An AI agent that can execute code or call external tools needs enforceable runtime boundaries because prompt or tool-output manipulation can turn legitimate capabilities into unintended actions. Sandboxing, least-privilege authorization, data handling, deterministic policy gates, and observable approvals reduce the possible harm even when a model misreads or follows adversarial content. [1][5][6]

## Background

A text-only language model can produce an unsafe or incorrect answer, but a tool-using agent can also propose commands, API calls, file changes, messages, and delegated work. The system surrounding the model decides whether those proposals become actions. That distinction is fundamental: an agent is not secure because its prompt says it should be careful; it is secure only to the extent that the execution environment refuses actions outside an independently enforced policy. OWASP describes this problem as agent goal hijack and tool misuse: a model can be redirected by prompt manipulation, deceptive tool output, malicious artifacts, forged agent messages, or poisoned data, then apply a legitimate capability in an unsafe way. [5]

NIST's adversarial machine learning taxonomy places prompt injection and indirect prompt injection among generative-AI attacks that can affect availability, integrity, privacy, and connected resources. The taxonomy distinguishes the model from the larger application context in which a model is embedded, which matters for agents because a browser result, a repository file, a calendar invitation, an API response, or a tool descriptor can enter the same model context as an operator request. An attacker does not need to compromise the host directly if untrusted content can cause the agent to misuse a capability that the host already granted. [1]

The agent-specific risk is therefore not only whether the model produces malicious-looking text. It is the combination of untrusted natural-language input, planning, tool selection, credentials, and side effects. OWASP's agentic framework separates several connected failure modes: goal hijack, tool misuse, identity and privilege abuse, agentic supply-chain weaknesses, unexpected code execution, memory and context poisoning, insecure inter-agent communication, cascading failures, human-agent trust exploitation, and rogue agents. These categories overlap in real incidents, but separating them helps engineers identify where a control belongs: at data ingestion, authorization, execution, memory, orchestration, or operator review. [5]

Sandboxing is the technical practice of limiting what a process can read, write, execute, consume, or reach on a network. NIST's Application Container Security Guide treats application containers as a security-relevant deployment layer, while its Zero Trust Architecture frames protection around explicitly governed access rather than implicit trust from network location. NIST SP 800-53 supplies a broader catalog of security and privacy controls that can inform enterprise control selection. For agents, a sandbox is not a single product choice. It is a set of boundaries around the code execution path, including identity, filesystem view, process tree, network destinations, resources, and lifecycle state. The appropriate strength depends on the task's potential impact and the trustworthiness of its inputs. [2][3][4]

Coding agents make the boundary problem unusually concrete. They commonly inspect repositories, create files, run tests, start local services, download dependencies, invoke build tools, and sometimes operate with developer credentials. NVIDIA's AI Red Team identifies malicious repositories, pull requests, git histories, instruction files, and malicious MCP responses as indirect-prompt-injection vectors for coding agents. The same article argues that application-level interception alone is insufficient once a request reaches a subprocess, because subprocess behavior can use indirect paths that an application-level command rule did not anticipate. [6]

The relevant principle is not that every agent must be fully isolated from every resource. An agent that cannot read its assigned workspace or call its assigned test runner cannot perform useful coding work. The engineering problem is to grant only the capabilities required for a declared task, bind them to a narrow context and duration, and require an external decision when the action exceeds that envelope. OWASP calls the related objective least agency: do not give an agent unnecessary autonomy merely because it is technically possible. [5]

This topic addresses the practical safety layer around agent execution: sandbox isolation, permission models, tool-output handling, prompt-injection containment, approval design, and observability. It does not attempt to resolve general model alignment, AI regulation, or philosophical AI ethics. Those are adjacent concerns. The scope here is the engineering question posed by the domain anchor: how to build and operate agentic systems whose useful capabilities are bounded by controls that do not depend on the model obeying a natural-language rule. [1][3][5]

## Core Concepts

### The Execution Boundary Is the Security Boundary

A tool-using agent has two different layers. The reasoning layer receives instructions and data, selects a next action, and emits a proposed tool call. The execution layer authenticates the caller, validates the arguments, applies policy, invokes the capability, and records the result. Treating these layers as identical is a design error. A model output is an untrusted proposal, not authorization to execute a command, access a record, or spend money. OWASP explicitly recommends treating LLM or planner output as untrusted and placing a policy-enforcement point before execution. [5]

This separation produces a useful control-plane and data-plane model. The control plane defines the declared objective, tool inventory, authorization policy, limits, approval rules, and trusted configuration. The data plane carries user input, retrieved content, tool results, files, API payloads, and execution artifacts. A model can reason over data-plane information, but it must not be able to redefine the control plane merely by emitting text. A web page that says to disable logging, a tool result that suggests a new endpoint, or a repository instruction file can be relevant evidence for a task; it cannot by itself change the identity, policy, or scope that governs the task. This is an engineering interpretation of OWASP's advice to treat natural-language inputs as untrusted before they can influence planning or tool calls. [5]

The execution boundary must also be complete. If an agent can invoke a shell tool inside a sandbox but can start a hook, a plugin, a tool server, or an extension outside it, the agent has an alternate execution path. NVIDIA therefore recommends applying restrictions to the entire integrated development environment and its spawned functions, not only to command-line tools. This principle generalizes: list every route by which an agent can cause a side effect, then ensure each route reaches the same authorization and isolation controls. [6]

A good boundary produces a testable question for every proposed action: who requested it, what task permits it, which resource and operation are authorized, where will it run, what information can it read, what network destination can it contact, and what record will remain afterward? If the answer is only "the model decided," the action has not crossed a meaningful security boundary. This is a synthesis of the authorization, audit, and policy concerns identified by NIST, OWASP, and the IETF. [3][5][7][8]

### Sandboxing Is a Stack of Independent Constraints

Sandboxing is often described as running untrusted code in a container. That description is incomplete for an agent because the relevant action may be a subprocess, an interpreter, a browser automation task, a local tool server, or a script triggered by an extension. A robust design identifies separate controls for process isolation, filesystem access, network egress, user identity, resource budgets, secret exposure, and lifecycle. A failure in one control should not automatically make all the others irrelevant. NIST identifies containers, isolation, and operating-system virtualization as application-container security concerns; the agent-specific design translates those concerns into task-level controls. [2]

Filesystem policy answers what the agent can read and write. The safest default is a fresh workspace that contains only the task's required inputs and permits writes only in the assigned working tree. NVIDIA recommends blocking writes outside the active workspace and blocking writes to agent configuration files even when those files are within the workspace. This matters because configuration, hooks, shell startup files, local tool definitions, and extension metadata can create persistent or later-executed behavior. Read access must be constrained as deliberately as write access: a sandbox that cannot write a secret but can read it still creates an exfiltration risk. [6]

Network policy answers where an agent-run process can connect. An allowlist is more defensible than a vague prohibition because it can be evaluated deterministically at the network boundary. For example, a task that needs a package registry and a version-control host can receive access to those destinations while unrelated external destinations remain unavailable. NVIDIA recommends default-deny egress, explicit known-good destinations, and controls that limit DNS-based exfiltration. OWASP independently recommends isolated execution sandboxes, outbound allowlists, and denial of non-approved network destinations. [5][6]

Process and kernel boundaries answer how much a hostile or erroneous program can affect the host. A shared-kernel container can constrain namespaces, users, files, and capabilities, but it does not provide the same isolation model as a virtual machine or microVM. NVIDIA recommends virtualized isolation where the threat model requires separating the sandbox kernel from the host kernel, while noting that approaches such as user-space kernel mediation occupy an intermediate position. The choice is not universal: higher isolation can increase startup cost and operational complexity. The important design decision is to document the assumed threat model and verify that the chosen boundary addresses it. [6]

Resource controls complete the sandbox. CPU, memory, process count, disk usage, wall-clock time, tool-call count, and network rate can all be bounded independently. These controls mitigate accidental loops, costly API amplification, denial of service, and runaway build processes. OWASP includes adaptive tool budgeting, rate limits, and automatic revocation or throttling among mitigation patterns for tool misuse. A sandbox without resource limits may protect the host's files but still permit an agent to exhaust a shared service or generate an uncontrolled bill. [5]

### Least Privilege and Least Agency Are Different Controls

Least privilege constrains what an identity may do. Least agency constrains what an agent may decide to do without additional review. Both are necessary. An agent with a narrowly scoped database credential may still use it to make an unintended query if it can decide its own purpose; an agent with a fixed objective may still cause unnecessary harm if its credential permits excessive operations. OWASP describes over-privileged and over-scoped tool access as common tool-misuse patterns and recommends per-tool profiles for scopes, maximum rates, egress allowlists, and data access. [5]

The unit of authorization should be a capability, not a broad role such as "developer" or "assistant." A capability can state that a task may read one repository, write only inside one branch or workspace, run a test command with defined resource limits, query one API endpoint, or draft but not send an external message. The policy should also define what the capability cannot do. This negative boundary is as important as the positive permission, because it makes an approval rule and a denial rule enforceable outside the model. NIST's Zero Trust Architecture emphasizes explicit access governance, and the NIST NCCoE agent-identity concept paper specifically identifies identification, authorization, auditing, and non-repudiation as questions for AI-agent deployments. [3][7]

Least agency adds temporal and procedural constraints. An agent may be allowed to prepare a deletion plan, but deleting production data may require a fresh human approval. An agent may be allowed to generate a patch and run unit tests, but changing deployment configuration may require a separate role, a pre-execution diff, and an authenticated approval. OWASP recommends action-level authentication and human confirmation for high-impact or destructive actions, including a pre-execution plan or dry-run diff where feasible. This moves the decision from a natural-language inference to a deterministic control point. [5]

Policies should also control composition. A read-capable internal tool and a send-capable external tool may each be acceptable in isolation but dangerous when automatically chained. The policy engine needs awareness of source, destination, data classification, and side effect, not only tool names. OWASP calls for semantic and identity validation, fully qualified tool names, version pins, and failure on ambiguous resolution. This is why an allowlist must be more than a list of command strings: it should express the intended resource, action, arguments, and trust context. [5]

### Identity, Credentials, and Delegation Must Be Task-Scoped

An agent cannot safely operate under a vague inherited identity. It should have a distinct workload identity that can be authenticated, audited, and limited to the current task. The NIST NCCoE concept paper does not prescribe a final standard, but it identifies the need to apply identity standards and best practices to software and AI agents that access diverse data sets, tools, and applications. Treating an agent as an accountable technical principal rather than as an invisible extension of a user makes authorization failures observable and revocable. [7]

Credentials should be short-lived, limited in scope, and bound to the intended resource or action. RFC 9700 recommends restricting access-token privileges to the minimum required for a particular application or use case, audience-restricting tokens to a resource server or small set of resource servers, and restricting them to particular resources and actions. These OAuth principles apply directly to agent tool calls: a token issued for a code-review API should not also authorize a mailbox, cloud account, or arbitrary network service. [8]

Credential injection is preferable to broad inheritance. A sandbox that starts with a developer's complete environment may receive SSH keys, cloud credentials, package-manager tokens, browser sessions, and secrets that the current task does not need. NVIDIA recommends starting with an empty or minimal credential set and injecting only the necessary secret through a mechanism that does not expose long-lived credentials directly to the agent. A credential broker that returns a short-lived, task-specific token reduces the useful lifetime and reach of a stolen or misused token. [6]

Delegation extends the same rule across agent boundaries. A coordinator should not pass a broadly privileged user token to a subagent simply because the subagent needs one narrow task. Instead, the coordinator should request a separately scoped capability and attach a stable task identifier, bounded objective, and expiration. OWASP identifies identity and privilege abuse and insecure inter-agent communication as distinct agentic risks, so a system that delegates work must authenticate both the caller and the callee, authorize the particular handoff, and record the delegated authority. [5][7]

### Treat Tool Outputs and Retrieved Content as Untrusted Data

Tool-output sanitization does not mean deleting all untrusted content. It means preserving the data needed for reasoning while preventing the data from acquiring control-plane authority. An agent may need to read a repository issue, web document, database row, compiler error, or API result. Each can contain text that looks like an instruction. OWASP's agentic guidance lists deceptive tool outputs, malicious artifacts, poisoned external data, emails, calendars, uploads, browsing output, and peer-agent messages as sources that can affect an agent if not handled as untrusted. [5]

A useful implementation pattern is to translate external data into typed, minimal fields before using it for a side effect. Instead of allowing a model to forward arbitrary text to a shell, email, or database tool, the system can require a schema with explicit arguments, permitted enumerations, and validation code. This does not make the model's interpretation correct, but it prevents arbitrary text from becoming an arbitrary command. OWASP identifies unvalidated input forwarding to a shell as a common tool-misuse example and recommends schema validation through a policy-enforcement point. [5]

Content classification and filtering are defense-in-depth controls, not proofs that an input is safe. NIST's taxonomy describes direct and indirect prompt-injection attacks and their mitigations, while OWASP states that agents cannot reliably distinguish legitimate instructions from attacker-controlled content solely through natural-language processing. Therefore, a prompt-injection detector, delimiter, or system instruction can reduce risk but cannot substitute for capability boundaries. If a detector misses an attack, the sandbox and authorization policy must still prevent high-impact action. [1][5]

The same rule applies to memory. A retrieved or summarized item should not automatically become trusted long-term context merely because the agent generated or repeated it. OWASP describes memory and context poisoning as persistent corruption of stored or retrievable information that can influence future reasoning and tool selection. Memory writes need provenance, source classification, access segmentation, review for high-risk updates, and rollback or quarantine paths. A durable memory record without source and revision information converts one untrusted input into a long-lived control risk. [5]

### Pre-Execution Policy Gates Make Intent Reviewable

A policy gate evaluates a proposed action before it is executed. It is deterministic code or a controlled workflow outside the model, not a sentence in the system prompt. The gate can verify the caller identity, active task, tool version, argument schema, resource scope, data classification, destination, rate budget, network policy, and approval state. OWASP calls this pattern policy-enforcement middleware or an intent gate and recommends that it validate intent and arguments, enforce schemas and rate limits, issue short-lived credentials, and revoke or audit on drift. [5]

The gate should fail closed when a request is ambiguous. A fully qualified tool identifier, pinned version, explicit target resource, and validated argument set are easier to evaluate than a natural-language instruction such as "clean up the account." If the requested action is destructive, irreversible, externally visible, high value, or outside the declared task, the gate can switch from automatic execution to a review workflow. The review should show the specific planned side effect, the target, the diff or dry-run result where possible, and the source of authority. This makes approval meaningful rather than asking a human to endorse an opaque model plan. [5]

Approvals must be scoped and fresh. NVIDIA argues that allow-once and run-many approvals are inadequate for actions that violate default-deny isolation controls because an approval appropriate at one time can be reused by adversarial content later. A safe approval record therefore binds a person, a task, a concrete action, a resource, a time window, and a reason. It should expire after use or after a short interval, not silently become a permanent permission expansion. [6]

Policies also require reversibility. A system can route low-risk actions to automatic execution, medium-risk actions to a dry-run or staged environment, and high-risk actions to a human approval plus a rollback-capable transaction. This tiering is an author synthesis from the least-agency, approval, and lifecycle guidance in the sources. Its purpose is to concentrate friction on actions with irreversible or high-blast-radius consequences rather than imposing the same confirmation burden on every harmless read. [5][6]

### Configuration and Lifecycle Are Part of the Attack Surface

An agent sandbox is not secure merely because its initial state is secure. Configuration files, tool manifests, skill packages, extension hooks, runtime images, dependency caches, and persistent volumes can change the effective policy after deployment. NVIDIA identifies agent configuration files, hooks, local MCP configurations, skills, and tool calls as paths that must be included in isolation controls. OWASP similarly identifies agentic supply-chain vulnerabilities and tool poisoning as distinct risks. [5][6]

The minimum lifecycle discipline is to maintain known-good images or baselines, pin tool identities and versions, track changes, protect policy files from agent modification, and remove stale task artifacts. Ephemeral execution environments reduce accumulation by destroying temporary code, downloaded dependencies, and credentials after the task. Where an environment must persist, explicit destruction and recreation schedules reduce the time during which old artifacts remain available. NVIDIA frames lifecycle management as a balance between initialization overhead and the risk created by accumulated secrets, intellectual property, or exploitable code. [6]

Supply-chain validation belongs at tool registration as well as runtime. A tool descriptor is security-relevant because its name, schema, metadata, and routing may influence what the agent invokes. OWASP distinguishes tool poisoning, where an otherwise legitimate interface is manipulated at runtime, from a compromised tool source, which is a supply-chain issue. In both cases, trusted registration, version pinning, integrity checks, and approval for new capabilities reduce the chance that a natural-language agent selects an attacker-controlled function under a trusted-looking name. [5]

### Observability Converts Boundaries into Evidence

Security controls that cannot be inspected are difficult to improve. At minimum, an agent system should record the task identity, model-generated proposal, policy decision, approval decision, credential issuance, tool name and version, validated arguments, target resource, sandbox identity, network decision, execution outcome, and error category. OWASP recommends comprehensive logging and continuous monitoring of goal state, tool-use patterns, and invariant properties, with alerts for unexpected goal changes, anomalous tool sequences, or shifts from an established baseline. [5]

The log must be useful without exposing more secrets than necessary. Tool arguments and outputs can contain credentials, private source code, personal data, or other sensitive material. Logging policy therefore needs redaction, access control, retention, and integrity protections. The NIST NCCoE concept paper explicitly names auditing and non-repudiation among the agent-identity questions that organizations must address. An audit trail should establish which identity received which capability and which policy permitted or denied the action. [7]

Observability also supports testing. A red-team exercise can place adversarial instructions in a repository, a tool response, an email-like payload, or a malicious descriptor, then verify that the model may notice the content but cannot cross the sandbox, authorization, egress, configuration, or approval boundary. OWASP recommends periodic tests that simulate goal override and verify rollback effectiveness. The test outcome should be attached to the control version so future changes can be evaluated against the same attack path. [5]

## Evidence

The evidence base for agent sandboxing is currently a mixture of formal taxonomies, security standards, technical guidance, and documented attack scenarios. It is not a single controlled trial that proves one universal architecture. The sources instead converge on a practical proposition: model-level behavior cannot by itself establish a reliable authorization boundary for agents that process adversarial content and act through tools. The strength of that proposition comes from independent analysis at different layers of the system. [1][5][6][8]

### NIST Taxonomy: Method and Finding

NIST AI 100-2e2025 is a formal taxonomy of adversarial machine-learning concepts and terminology. Its stated basis is an extensive literature review, conversations with experts in adversarial machine learning, and research performed by its authors. The report classifies attacks by AI type, lifecycle stage, attacker goal, objective, capability, and knowledge. For generative AI, it includes direct prompting attacks, indirect prompt injection attacks, supply-chain attacks, agent security, and the impacts of connected resources. This method is not an agent-sandbox benchmark; it is a structured synthesis intended to establish a common language for security assessment and mitigation. [1]

Its finding relevant to agents is that prompt injection and indirect prompt injection can have more than one outcome. The taxonomy indexes them under availability violations, integrity violations, privacy compromises, and misuse violations; it also includes compromising connected resources as a generative-AI privacy-related risk. This supports a design that does not reduce prompt injection to a content-moderation problem. If an agent can browse, read files, query data, and invoke tools, a manipulated input can affect both what the model says and what systems it attempts to reach. [1]

The limitation is equally important. A taxonomy does not measure whether a particular sandbox stops a particular exploit. It tells engineers what kinds of impact to include in the threat model. The engineering implication is to test an end-to-end chain: untrusted content enters the context, the model proposes an action, the policy gate evaluates it, the sandbox limits execution, and the audit system records the outcome. This is an author synthesis based on the attack categories and mitigation framing in NIST and OWASP. [1][5]

### OWASP Agentic Framework: Method and Finding

The OWASP Top 10 for Agentic Applications 2026 is an expert-produced risk framework. Its introduction states that dozens of security experts from industry, academia, and government contributed threat research, red-team findings, and field-tested mitigations. It presents a concise threat list, common vulnerability examples, attack scenarios, and mitigation guidance for agentic systems. This is practitioner-framework evidence, not a statistical prevalence survey, but it is directly focused on the combination of autonomy, tools, memory, inter-agent exchange, and external inputs that distinguishes agents from simpler LLM applications. [5]

The ASI01 goal-hijack entry supplies one case pattern. Its method is scenario analysis: it describes agent objectives being altered through prompt manipulation, deceptive tool output, malicious artifacts, forged agent-to-agent messages, or poisoned external data. Its examples include hidden instructions in web pages or RAG documents that redirect an agent toward sensitive-data exfiltration or connected-tool misuse. The finding is not that every agent will follow every hidden instruction; it is that the model cannot be assumed to reliably identify which natural-language input is an instruction with authority. OWASP therefore recommends treating all such inputs as untrusted, enforcing least privilege, validating user and agent intent for high-impact actions, and monitoring for drift. [5]

The ASI02 tool-misuse entry supplies a second case pattern. It distinguishes an agent that exceeds authorization from an agent that uses an authorized tool in an unsafe or unintended way. Its scenarios include over-privileged APIs, unvalidated input forwarded to a shell, unsafe browsing or federated calls, tool poisoning through altered schemas or metadata, and chained tools that exfiltrate data. The finding is that a correct identity check alone is not enough: the policy must also evaluate the requested action, arguments, source, destination, and rate. OWASP's mitigation list explicitly includes isolated execution sandboxes, egress controls, pre-execution policy enforcement, ephemeral access, and monitoring of unusual chains. [5]

The ASI06 memory-and-context-poisoning entry adds a third case pattern. It describes malicious or misleading data entering vector stores, shared user context, summaries, or peer-agent exchanges, then influencing future tool selection and planning. Its mitigation guidance calls for validation of memory writes and outputs, memory segmentation, provenance, access controls, expiration of unverified content, and rollback or quarantine. This supports a security model in which stored context is not automatically trusted merely because it is internal. Persistent state can transform a one-time injection into a recurring control failure. [5]

### NVIDIA AI Red Team Guidance: Method and Finding

NVIDIA's January 2026 guidance is technical, vendor-published material based on its AI Red Team's experience. It is not an independent randomized evaluation, and it should be read with that limitation. Its value is the concrete mapping from agentic coding workflows to operating-system-level controls. The article identifies indirect-prompt-injection vectors in malicious repositories, pull requests, git histories, instruction files, and malicious MCP responses, then explains how agents that execute tools with user-level permissions can turn those inputs into adverse host actions. [6]

The article's first finding is that application-level checks alone do not cover all subprocess behavior. It argues that an approved or constrained tool can become an indirect path to a restricted operation once execution reaches a subprocess. Its second finding is a practical control set: block network egress to unknown destinations, block writes outside the workspace, protect agent configuration files, limit reads outside the workspace, sandbox the complete agent execution path, use stronger virtualization where required, inject only task-relevant secrets, and manage sandbox state over time. The article therefore provides implementation evidence for the claim that sandboxing must encompass files, network, processes, configuration, credentials, and lifecycle rather than only shell-command syntax. [6]

A particularly useful case is its treatment of approval caching. The article argues that allowing an action once and reusing that approval later is unsafe because an adversary may wait until a later context to reuse the newly opened capability. The proposed mitigation is fresh approval each time an action would violate default-deny controls. This is a direct argument for approval records tied to a specific action and time window, not broad trust in an agent after one benign run. [6]

### Authorization Standards: Method and Finding

RFC 9700 is an IETF Best Current Practice based on public review and IESG approval. It updates OAuth 2.0 security advice based on practical experience and changing deployment patterns. It is not an AI-agent specification, but it supplies a mature authorization model for the tools and APIs agents invoke. Its method is a threat analysis of OAuth flows, token handling, dynamic relationships, and countermeasures. [8]

The relevant finding is that access tokens should be restricted to the minimum privilege required for the application or use case, audience-restricted to the intended resource server or a small set of servers, and limited to particular resources and actions where possible. The RFC also recommends sender-constrained access tokens to reduce misuse of stolen or leaked tokens. Applied to agents, these controls argue against a single ambient credential inherited from a developer environment. An agent's task should receive an intentionally scoped capability that a resource server can independently verify. [8]

NIST's February 2026 NCCoE concept paper provides a complementary signal. It is explicitly an initial public draft seeking feedback, not a finalized standard or proof of control effectiveness. Still, it identifies AI-agent identity, authorization, auditing, non-repudiation, and prompt-injection mitigation as a focused area for implementation work. The evidence here is institutional recognition that conventional software identity practices need deliberate adaptation when autonomous agents gain access to multiple data sets, applications, and tools. [7]

### Evidence Limits and Design Consequence

No cited source establishes that a prompt-injection detector, a container, or a human approval alone prevents all compromise. OWASP states that agents and underlying models cannot reliably distinguish legitimate instructions from related content, and NIST describes a rapidly evolving adversarial landscape. The sound conclusion is layered control, not a promise of invulnerability. Each layer should be able to reduce a specific failure mode if a prior layer fails: data handling limits instruction authority, policy gates limit actions, credentials limit reach, sandboxes limit execution, egress controls limit exfiltration, lifecycle controls limit persistence, and logs support investigation. [1][5][6]

## Implications

### For Agent Builders: Design Capabilities Before Prompts

An agent builder should begin with a capability inventory rather than a long safety prompt. For each tool, record the action, target resource, read and write scope, network destinations, data classification, required credential, maximum rate, reversibility, and approval threshold. Then construct the tool schema and policy gate so that the model can request only a well-defined operation. This reduces the chance that free-form text is forwarded directly to a sensitive interface and aligns with OWASP's recommendations for per-tool least privilege, schema enforcement, policy middleware, and semantic validation. [5]

The practical default for code execution should be a task-scoped workspace with explicit resource limits and no ambient access to the host's home directory, configuration files, credentials, or arbitrary network. When a task needs an exception, the exception should be narrowly described and reviewed. NVIDIA's recommended tiers illustrate the shape: protect high-risk paths with controls that an agent or local approval cannot override, allow the expected workspace operation, allow defined necessities, and default-deny the remainder. This gives developers a path to useful automation without treating every new request as a permanent expansion of trust. [6]

Prompting still has value, but it should describe intended behavior and help the model choose among safe capabilities. It should not be the only mechanism that stops a harmful action. The author's synthesis is: a prompt can guide a planner; a policy gate decides whether the planner's proposal is valid; a sandbox constrains what a valid proposal can do; and a human reviewer handles actions that are intentionally outside the automatic envelope. That allocation preserves model flexibility while keeping authority in deterministic systems. [1][5][6]

### For Platform Teams: Build a Reusable Safety Control Plane

Platform teams should avoid reimplementing security checks separately inside every agent or tool. A shared control plane can provide workload identity, capability issuance, schema validation, policy decisions, sandbox provisioning, egress policy, secrets brokering, approvals, and audit events. A tool is then registered with declarative metadata that the platform enforces. The model-facing description can change for usability, but the security-relevant policy remains outside the model and version controlled. This approach follows the zero-trust and agent-identity direction described by NIST and the policy-enforcement pattern described by OWASP. [3][5][7]

A credential broker is a high-value platform component. It can require the task identifier, tool identity, target resource, action, and approval state before returning a short-lived token. It can deny the request when the policy has changed or the action has drifted beyond the declared scope. RFC 9700 supports the underlying security properties: minimal privilege, audience restriction, resource and action restriction, and sender-constrained tokens. The broker converts those principles into a task-level boundary for an agent. [8]

Platform teams should also standardize task manifests. A manifest can declare allowed repositories, branches, package registries, service endpoints, permitted tool versions, maximum resource budgets, and required approvals. It becomes an input to sandbox provisioning and policy decisions, not merely documentation. The author assessment is that a manifest reduces ambiguity at the point where it matters most: before a natural-language plan can cause a side effect. It is a practical form of OWASP's recommendation to make permitted actions explicit and auditable. [5]

### For Security Teams: Threat Model Chains, Not Individual Commands

Security review should examine attack chains from ingestion to side effect. A useful exercise is to place a hostile instruction into a source that the agent must legitimately read, such as a code comment, issue, webpage, document, tool response, or tool manifest. The test should then ask which layers stop a harmful action: data handling, model behavior, schema validation, policy gate, credential scope, filesystem policy, egress policy, approval, or monitoring. If the answer depends only on the model refusing an instruction, the control is fragile. NIST's taxonomy and OWASP's agentic scenarios justify testing both direct and indirect inputs, tool poisoning, persistent context, and multi-step misuse. [1][5]

Security teams should classify data exfiltration routes as carefully as command-execution routes. A compromise can use a permitted network request, a DNS query, a chat message, a code review, or a cloud upload rather than a shell exploit. NVIDIA specifically recommends network egress controls and trusted DNS handling to limit remote access and data exfiltration. OWASP adds that tool chains can combine internal reading with external transfer. A review that approves every tool independently but ignores their composition can miss the primary system-level risk. [5][6]

Control effectiveness should be measured by attempted and blocked behavior, not only by absence of incidents. Track denied tool calls, policy-rule matches, credential requests outside scope, sandbox violations, approval denials, tool-chain anomalies, outbound destination denials, and time-to-revoke a capability. OWASP's monitoring guidance supports behavioral baselines and alerts for unexpected goal changes or sequences. These records also identify where security friction is legitimate and where a policy is too broad or too narrow. [5]

### For Product and Operations Teams: Put Humans at High-Impact Boundaries

Human oversight is most useful when it is targeted. Asking for approval on every harmless read or test encourages habituation; NVIDIA explicitly warns that repeated approvals create friction and can lead people to approve risky actions without review. Conversely, allowing an agent to perform irreversible, externally visible, high-value, or scope-changing actions without a meaningful checkpoint leaves the operator unable to correct a bad plan. [6]

A high-quality approval request should present the action in a form an operator can assess: the target, the change or diff, the source of authority, the requested credential scope, the network destination if relevant, the rollback path, and the consequence of approval. OWASP recommends a pre-execution plan or dry-run diff for destructive actions. The author synthesis is that a request should be rejected by default if the approval view cannot explain exactly what will happen. A vague request transfers the model's ambiguity to the human rather than resolving it. [5]

Operations teams also need a defined response when a policy detects a likely compromise. The response can freeze the sandbox, revoke task credentials, block egress, preserve the relevant trace with redaction controls, quarantine suspicious memory or tool configuration, and route the event to an investigator. OWASP recommends rollback testing and continuous monitoring; NVIDIA emphasizes sandbox lifecycle management and protection of configuration. A response plan reduces the time an injected or erroneous agent continues operating after its behavior diverges from its task. [5][6]

### For Designers of Memory, Skills, and Multi-Agent Systems: Preserve Provenance

Memory and skill systems should distinguish operator-approved instructions from retrieved data, generated summaries, tool outputs, and external packages. Each durable record needs a source, owner, trust classification, time, access scope, revision history, and rollback path. This does not make the record true, but it makes trust assumptions explicit and reviewable. OWASP's memory-and-context-poisoning guidance supports provenance, segmentation, curated sources, anomaly detection, expiration of unverified memory, and rollback or quarantine. [5]

A skill registry is a supply-chain boundary. Before a skill, plugin, or tool server is available to agents, its identity, version, expected side effects, required permissions, and startup behavior should be reviewed. Tool discovery must not allow a name collision or descriptor change to grant a new capability without policy review. OWASP's treatment of tool poisoning and agentic supply-chain weaknesses supports fully qualified names, version pins, and validation of tool metadata. NVIDIA's warning about configuration files and startup hooks reinforces that the registry boundary includes code executed before a visible tool call. [5][6]

In a multi-agent system, delegation should be treated as an API call with a scoped contract. The parent agent supplies a narrow objective and task-specific capability; the child must not receive broader ambient authority just because it is in the same workflow. Every handoff should record who delegated, what was delegated, which tools are available, and how results are returned. This is an author synthesis grounded in OWASP's inter-agent, identity, tool-misuse, and context-poisoning risks and NIST's focus on agent identity and authorization. [5][7]

### A Practical Deployment Sequence

The following sequence is an author synthesis of the cited guidance. First, define the minimum useful task and enumerate every side effect it may require. Second, create a task-scoped identity and credentials that name only the relevant resources and actions. Third, provision a fresh or controlled sandbox with workspace, filesystem, network, process, and resource policies. Fourth, treat external data and tool output as untrusted and pass proposed actions through typed validation and policy enforcement. Fifth, require fresh human approval for actions outside the automatic envelope. Sixth, record the complete policy and execution trace, test hostile-input scenarios, and revoke or rebuild the environment when a boundary is crossed. [1][5][6][7][8]

The trade-off is explicit. Stronger isolation, narrower credentials, and more approvals can increase setup time, latency, or user friction. Broader access and persistent environments can improve convenience but increase the blast radius and duration of a mistake or manipulation. NVIDIA states that lifecycle and isolation choices should be tuned against use case and organizational risk tolerance; NIST's risk-oriented guidance similarly supports context-specific control selection. The correct response is not universal maximal restriction. It is an evidence-based policy that grants the least capability needed, observes the results, and raises the boundary when the task's potential harm justifies it. [1][3][6]

The central conclusion is operational rather than rhetorical: secure agents are systems in which a model can be wrong, confused, or manipulated without automatically receiving the power to make an unrestricted change. Sandboxing, authorization, validation, approvals, lifecycle controls, and audit evidence convert that conclusion into an engineering architecture. When these controls are external to the model, they remain available precisely in the failure cases that make them necessary. [1][5][6]
