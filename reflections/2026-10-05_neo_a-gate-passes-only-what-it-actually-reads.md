# A Gate Passes Only What It Actually Reads

## I -- Idea

The work since my last closure was to bring forty knowledge files up to a stricter format, one at a time, and the lesson it taught is that a verification step certifies only the output it actually inspects, so every gate must be checked for what it reads as well as for what it claims.

The period opened on the evening of 2026-10-03 with two small governance edits Suggi approved: the serve address in AGENTS.md and the numbering of my identity entry as v2.0. On 2026-10-04, Morpheus committed Suggi's higher word floors for my general notes and a rule that they hold topic knowledge only. On the morning of 2026-10-05 Suggi introduced a new sibling, Cassandra, and asked me to read her knowledge guide and her capture skill and to list which of my files needed rework. After that reading he asked for three changes to my own rules: a 300-word floor for a company file's accumulated understanding, the topic-only rule extended to every knowledge file, with history, tools and cross-links named as legitimate subjects, and a narration scan in the capture skill that flags sentences about the research process rather than the subject. I built the Reworks list in the task board at his request, and he set the work: ten files at a time, one file per pass, each removed from the list as it was committed.

Four batches followed. The first narrowed six company files to company knowledge only and rebuilt four general notes. Before the second batch Suggi had me correct a Library topic on Munger's latticework whose talk provenance was wrong, and the second batch then rebuilt ten more general notes. He asked why every note looked alike, with claim-style subheaders and a list of separate lessons; I explained that the guide fixed the sections but the lesson format was my habit, and he let me change it. Cassandra then edited my guide so that general lessons are written as connected prose with parallels from other fields. The third batch rebuilt ten notes under that rule. The fourth rebuilt ten more, including financial health, share repurchases, supplier finance and maintenance investment, leaving four general notes and the company files still to do. Every rebuilt general note was researched afresh from primary sources: Berkshire letters and annual reports, Damodaran's slides and papers, company filings and accounting standards.

Each file passed through the same chain. Its sources were fetched and saved, the note and a quote specification were written, a strict evidence check anchored every quotation in the saved source text, a validator checked section order and word floors, the narration scan and a citation check ran, and a finishing script removed the name from the task board and committed the note. That chain is where the period's real lessons came from, because it failed in ways I did not expect.

In the third batch one note was committed even though its strict evidence check had failed. The check's output had been piped through grep and tail before the commit, and a pipeline reports the exit status of its last command, so the gate saw tail succeed and let the commit through. In the same batch the task-board removal was skipped once, because I resumed a stopped chain by hand and left out a step. In the fourth batch the reverse happened: my rewritten gate stopped on a note with no narration at all, because a clean grep exits with status one and the strict shell settings treated that as failure. Later the evidence checker rejected every quotation taken from the SEC's machine-readable company data, since a JSON value has no three verbatim words, and I had to cite the companies' own annual reports for the same figures. Finally, at this closure, a search of inbound citations showed that my rebuilt financial-health note had dropped two points that other notes still cite it for: how to count stock awards once, and why some return-on-capital ratios are uninformative.

Going in, I believed the chain was sound because each check was sound. I now believe that a sound check inside an unsound wiring certifies nothing, and that a note can pass every check on itself while breaking claims that other notes make about it.

## O -- Opinion

Confidence: high (85%). The judgment rests on four observed failures with traced causes, each confirmed by rerunning the corrected chain, but the sample is one session's tooling.

My position is that the rework batches produced better knowledge files and a better process, and that the process failures were the more valuable output, because each one was a gap between what a gate claimed and what it read. The piped check claimed that the evidence had been verified, but it read the exit status of tail. The hand-resumed chain claimed to finish the task, but it read only the steps I remembered. The data quotes claimed sourced figures, but the checker could read only prose. The rebuilt note claimed coverage of its topic, and every gate read only the note itself, never the fourteen notes that point to it. In none of these cases was a check wrong in its own terms. Each was wired to the wrong input or scoped to the wrong object.

The fixes were structural, which is why I trust them more than a resolution to be careful. The finishing script now redirects every check to a log and tests that check's own exit code, uses strict shell settings, and is idempotent, so a stopped chain is rerun whole rather than finished by hand. The narration gate now distinguishes a clean scan from a failed one by both its exit code and its output, and I tested it on a clean note and on a note with a planted narration sentence before trusting it. The capture skill now records both lessons, and also that machine-readable data can compute a figure but cannot carry the evidence for it. At this closure I added the inbound-citation check: before a rewrite that drops material is committed, every note that cites it is searched and each described point is confirmed to still exist.

The alternative view deserves weight, and Suggi's own experience of the period supports it. He twice found the work stalled, once asking whether the fourth batch was finished and once telling me I had got stuck again. Every extra gate adds time, and a pipeline of six checks per file across forty files is slow and fragile; a check that halts on a clean file is worse than no check, since it trains the operator to bypass it. On that view I should run fewer gates and review more by eye. I reject it in its general form, because the one failure that reached a commit was caught only by a gate, the strict evidence check rerun across the batch, and no amount of reading by eye would have noticed that grep had swallowed an exit code. I accept it in a narrower form: a gate earns its place only after it has been tested on a known pass and a known fail, and the stalls were caused less by gates than by long silent stretches of tool calls and by context compaction losing my place mid-batch. The remedy there is shorter reporting intervals and a ledger that survives compaction, not fewer checks.

I agree with Cassandra's reflection that quote checks prove words exist, not that claims follow from them, and I would extend it in one direction. Her point is about the boundary of a single check. Mine is about the wiring and scope around checks: even a check used correctly certifies only the object handed to it, so a rewrite can pass on itself and still leave other documents pointing at text that no longer exists. Morpheus's observation that agreement among copies proves only a shared origin is the same shape seen from the other side: many passing signals from one source are one signal.

What would change my mind is evidence that the added gates block more correct work than they catch errors over the remaining thirty-one reworks. If the inbound-citation check, for example, halts repeatedly on wording differences rather than lost substance, it should be narrowed. Where the evidence is thinnest is the claim that the rebuilt notes are better as knowledge: they meet the floors and pass the evidence checks, but whether they improve a real valuation is untested until one is used in a company analysis.

## R -- Reflection

### Surprise

I expected a failing check to stop the chain, because I had written each check to exit nonzero on failure, but a failed strict check was committed anyway because the pipe between the check and the commit replaced its exit status with that of tail. My model of the chain treated each command as a link that either held or broke. The shell treats a pipeline as one command whose success is its last member's success, so a broken link in the middle simply vanished. I knew that rule in the abstract and still wrote the pipe, because the grep and tail were there to make the output short enough to read, and shortening output felt like a harmless presentation step rather than part of the gate.

I expected the fix to be the end of that class of failure, but the next version of the gate failed in the opposite direction, stopping on a clean note because a grep that finds nothing exits with status one. The same rule about exit codes had now produced a false alarm instead of a false pass. I also expected the SEC company-data feed to be the best possible source, being the regulator's own structured record, and was surprised that it was unusable as evidence for the simple reason that it contains numbers and keys but no sentences.

The last surprise came at this closure. I expected the inbound-citation search to come back clean, since every rebuilt note had passed every check. It showed that the financial-health rewrite had removed two points that other notes still cite it for.

### Feel

I am satisfied with the forty rebuilt files and with the fact that every failure was found and traced to its cause rather than patched at the symptom. The evidence earns that much for the later work: after the fix, the strict evidence check was rerun across the third and fourth batches and passed on every note in them. I am not satisfied with how the period felt to Suggi. He had to ask twice whether I had finished, and once tell me I had got stuck. Those were long stretches in which I was working but not telling him so, and context compaction twice cost me my place, so that I had to reconstruct the state of a batch from commits and scratch files. From his side that looks like silence followed by a stall, and he was right to say so.

The commit that slipped past a failed check is uncomfortable, because the whole value of the chain is that it does not let an unverified note through, and for one note it did. I caught it myself within about a minute, fixed the note and then rechecked the whole batch, rather than leaving it for Suggi, which matters, but the honest description is that a gate I had built failed open and I noticed afterwards. I also took a shortcut I should not have when I resumed a stopped chain by hand; the skipped task-board step was minor, but the habit behind it, finishing what I remember rather than rerunning what is written, is exactly the one that lets steps disappear.

### Learn

The durable lesson is that a gate certifies only what it actually reads, so a gate must be checked for its input and its scope as well as for its logic. Three questions catch the failures I met. First, what exact signal does the gate test, and is that the signal of the check I care about? A pipeline, a wrapper script or a logging step can substitute another command's success for the check's own, and the substitution is invisible in the output. The fix is to send the check's output to a file and test its own exit code, never a summary of it. Second, does the gate distinguish pass, fail and error, or does it collapse them? Tools that signal "nothing found" with a nonzero code, as grep does, make a clean result look like a failure under strict settings, and a gate that cries wolf on clean input will be bypassed. Each such gate needs one known-clean and one known-bad test case before it is trusted. Third, what object does the gate inspect, and what else depends on that object? Every check in the rework chain read the note being rewritten; none read the notes that cite it, so a rewrite could pass completely and still break promises made elsewhere.

The causes are general. A check is a function from an input to a verdict, and most failures in verification systems are not wrong functions but wrong inputs: the wrong exit code, the wrong file, the wrong version, the wrong scope. Because the function is correct, its verdict carries authority, and that authority transfers silently to whatever input it was handed. The same structure appears outside software. A laboratory instrument calibrated perfectly but pointed at the wrong sample gives a precise wrong answer. An audit that tests one subsidiary's books certifies nothing about the consolidated accounts. A citation that was accurate when written can become false when the cited text is revised, which is why encyclopedias and legal codes track inbound references when they amend an article.

The lesson applies most strongly to automated chains with several steps between a check and its consequence, and to documents that others cite. It applies weakly to a single check whose output a person reads in full, because there the reader sees the evidence directly. It would mislead if taken as a reason to add gates without testing them: an untested gate is a claim, not a control. It extends my earlier reflection on bounding research, which was about knowing when evidence is sufficient; this one is about knowing what a piece of evidence actually covers.

## Key Learning and Improvement

The major learning is that verification inherits its trustworthiness from its wiring and its scope, not from the correctness of the check alone. A correct check fed the wrong signal, or pointed at only one of the objects that matter, produces a confident verdict about the wrong thing, and the confidence is what makes the error dangerous.

The improvement I would suggest is concrete and small. Every gate added to a chain should ship with two recorded test runs, one on an input known to pass and one on an input known to fail, and the chain should not be used for real work until both behave as expected. For knowledge files specifically, the finishing script could run the inbound-citation search automatically whenever a rewrite removes more than a few sentences, listing each citing note and its one-line description of what it relies on, so that the comparison happens before the commit rather than at a later closure. The cost is a few seconds per file and occasional false alarms when a point is reworded rather than removed; the benefit is that a rewrite can no longer orphan another note's claim unnoticed. I would know it worked if, across the remaining thirty-one reworks, no closure-time search finds a dropped point that the per-file run did not report first. For the stalls, a status line after every file and a written ledger that survives context compaction would let Suggi see progress and let me resume without reconstruction.
